# 💻 Робота з Кодовою Базою `@nan0web/payload-*`

Цей workflow описує стандарти написання коду та структурування плагінів у репозиторії `apps/payload-cms`.

## 1. Структура Пакета Плагіна

Кожен плагін у `<plugin-name>` дотримується стандарту **Payload 3.x ESM**:

```text
<plugin-name>/
├── package.json        # "type": "module", subpath exports
├── README.md           # Документація плагіна
├── src/
│   ├── index.js        # Головна функція-конфігуратор плагіна (Pure Logic)
│   ├── admin.js        # React/Next.js Admin UI компоненти (якщо є)
│   └── first-paint.js  # Inline DOM скрипти без гідрації (якщо є)
└── tests/              # Сценарні та юніт-тести плагіна
```

## 2. Відносні Шляхи (Strict Relative Paths Rule)

- **ЗАБОРОНЕНО використовувати абсолютні шляхи файлової системи** (`/Users/username/...` чи `C:\...`).
- Усі імпорти, посилання в документації та конфіги повинні використовувати **відносні шляхи** (`./src/index.js`, `../payload-self-storage`, `docs/workflows/README.md`).

3. **Принцип OLMUI (One Logic — Multiple UI)**

1. **`src/index.js` (Ядро/Логіка):** Експортує плагін-функцію, яка приймає `config` Payload і повертає оновлений `config`. Жодного React-коду тут немає.
2. **`src/admin.js` (UI Адмінки):** Експортує автономні React-компоненти для кастомізації адмін-панелі Payload (наприклад, Custom Nav, Custom Controls).
3. **`src/first-paint.js` (First Paint / Fast Execution):** Скрипти, що виконуються в браузері до гідрації React (наприклад, зчитування теми з `localStorage` в `<head>`).

## 4. Повна Ізоляція Логіки (TLI) та 100% Покриття Тестами

- **Total Logic Isolation (TLI):** Уся бізнес-логіка (маніпуляції з URL, нормалізація шляхів, обробка i18n, формати) розробляється як чисті ізольовані **агностичні до середовища (Environment-Agnostic)** функції Standard JS/TS, які можуть виконуватися в будь-якому рантаймі (Browser, Node.js, Deno, Bun, Edge Workers) без залежності від екземпляра сервера Payload чи DOM.
- **100% Coverage Requirement:** Уся чиста логіка у `src/` повинна бути повністю випробувана автономними юніт-тестами (`node:test`) із досягненням 100% покриття за гілками та операторами.
- **Мінімальний Таймаут Тестів (Minimal Test Timeout Rule):** Запуск тестів ЗАВЖДІ виконується з явним розрахунковим таймаутом (наприклад, `node --test --test-timeout=3000`). Заборонено використовувати нескінченні очікування або завищені знання, щоб AI-агенти та LLM-моделі не зависали на заблокованих процесах.

## 5. Специфікація Компонентів Admin UI у Payload 3.x

- **Рядкові Шляхи Компонентів (String Component Paths):** У Payload 3.x компоненти для `providers`, `views`, `beforeLogin`, `beforeDashboard` тощо реєструються **виключно через стандартні рядкові шляхи вида `pkg-name/subpath#ExportName`** (наприклад, `'@nan0web/payload-signin-theme-state/admin#ThemeProvider'`).
- **Заборона застарілих об'єктів:** Заборонено передавати компоненти як об'єкти `{ path: '...', clientProps: ... }` у конфігурації плагінів, оскільки це порушує генерацію `importMap` та реєстрацію у серверному контексті Next.js.
- **Підтримка Асинхронних Конфігів та Promises:** Конфігуратори-обгортки (на кшталт `withStorage`) повинні обов'язково підтримувати роботу з `Promise` та асинхронним `buildConfig`.

## 6. Кросплатформенність (Windows / macOS / Linux)

- Будь-який скрипт автоматизації інсталяції в `testing-app` або тестування повинен працювати однаково на Windows, macOS та Linux.
- Використовуйте `pnpm` та Node.js скрипти для міжплатформної сумісності замість чистого `bash`.
