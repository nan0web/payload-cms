# 🚀 Конвеєр Розробки Плагінів та Протокол Виробничої Міграції

Цей документ описує стандартизований конвеєр (pipeline) для розробки, інтеграційного тестування плагінів екосистеми `@nan0web/payload-*` та безпечного перенесення змін на продакшен-проєкти.

---

## 1. Ізоляція Контексту та Правила Роботи з Проєктами

1. **Стабілізація в `testing-app` перед продакшеном**:
   - Будь-який плагін чи архітектурна зміна спочатку розробляються, пакуються та повністю тестуються в песочнику `testing-app`.
   - Не дозволяється переходити до реальних виробничих сайтів до того, як `pnpm test` (unit-тести) та `pnpm test:int` (інтеграційні тести в `testing-app`) пройдуть на 100% без помилок.

2. **Окремий сеанс/чат під кожен виробничий проєкт**:
   - Заборонено вести розробку або міграцію кількох виробничих проєктів у межах одного діалогового вікна/сеансу.
   - Для кожного продакшен-проєкта створюється **окремий чат**.
   - Робота проводиться чітко у відповідній директорії проєкту (`/шлях/до/конкретного-проєкту`).

---

## 2. Обов'язковий Протокол Аудиту та Міграції Медіа (Media Migration Protocol)

При проведенні міграції медіафайлів (з урахуванням `payload-self-storage`, метаданих папок, ієрархічної структури диска та WebP-оптимізації) дотримуйтесь суворого алгоритму з двох етапів:

### Етап I: Read-Only Аудит (Без зміни даних)

Перед виконанням будь-яких команд модифікації проводиться повний збір інформації по 10 пунктах:

1. **Версія Payload CMS** (наприклад `3.87.1`).
2. **Database Adapter** (`postgresAdapter`, `mongooseAdapter`, `sqliteAdapter`).
3. **Конфігурація колекції `Media`** (поля, хуки, обмеження).
4. **Налаштування папок (`folders configuration`)** (наявність `folders: true` та зв'язок з `payload-folders`).
5. **Розміри зображень (`imageSizes`)** (перелік ширини, висоти, обрізки та опції форматів).
6. **Поточна структура сховища** (значення `staticDir`, `publicUrlPrefix`, фізичне розташування на диску).
7. **Статистика записів та файлів** (кількість документів у БД vs кількість файлів на диску).
8. **Виявлення проблемних файлів** (дублікати імен, осиротілі файли `orphan files`, відсутні оригінали чи мініатюри).
9. **Доступність бекапів та варіанти відновлення** (наявність дампу БД та архіву файлів сховища).
10. **Загальний обсяг даних** (розмір БД та фізичного сховища у байтах/ГБ).

### Етап II: План Міграції, Dry-Run та Безпечний Виконавчий Цикл

1. **Підготовка документації**:
   - Створення `migration_plan.md` з описом усіх кроків.
   - Підготовка сценарію **Dry-Run** (тестовий запуск без запису у БД та на диск з виводом логів змін).
   - Підготовка **Rollback Plan** (інструкція швидкого відновлення з бекапу).
2. **Отримання підтвердження**:
   - Зупинка виконання та очікування **окремого явного підтвердження від користувача**.
3. **Виконання на Staging / Копії**:
   - Перше виконання міграції проводиться **виключно на копії бази даних та сховища (Staging)**.
   - Тільки після успішної перевірки результатів на Staging міграція застосовується до продакшену.

## 3. Кращі Практики Розробки Плагінів (Payload CMS Best Practices)

На основі офіційних специфікацій Payload CMS (`payloadcms.com/llms.txt`) розробка плагінів підпорядковується наступним стандартам:

1. **Суворий Інженерний Стандарт Покриття Тестами (Strict 100% Coverage Rule)**:
   - **Total Logic Isolation (TLI)**: Уся чиста логіка плагіна (маніпуляції з URL, обробка редіректів, форматування даних, обчислення шляхів) ПОВИННА розроблятися як **агностичні до середовища (Environment-Agnostic)** функції Standard JS/TS (сумісні з Browser, Node.js, Deno, Bun, Edge Workers), повністю відокремлені від UI-компонентів та сервера Payload CMS.
   - **100% Покриття Тестами для Ядерної Логіки**: Ядерні функції плагіна у `src/` повинні бути покриті юніт-тестами на 100% (statement, branch, function coverage) за допомогою нативного `node:test` runner.
   - **Трирівневий Конвеєр Верифікації**:
     - **Рівень 1 (Юніт-тести & TLI)**: `pnpm test` у каталозі плагіна (`node:test`) без запуску БД чи Next.js.
     * **Рівень 2 (Контракт & Пакування)**: `pnpm pack:check` перевіряє цілісність субшляхів експорту (subpath exports) та сумісність з ESM.
     * **Рівень 3 (Інтеграція & E2E)**: `pnpm test:int` та `pnpm test:e2e` в `testing-app` перевіряють роботу плагіна у реальному середовищі з Postgres та Next.js.

2. **Стандарти Фреймворків Тестування**:
   - **`node:test` (Native Node Test Runner)**: Використовується у чисто автономних бекенд-пакетах (`packages/payload-*`) для юніт-тестів без зовнішніх залежностей (`pnpm test`).
   - **`vitest`**: Використовується у проєктах з UI/Next.js (`testing-app`) для інтеграційних тестів (`environment: 'node'`) та React/DOM компонентів (`environment: 'jsdom'`).

2. **Деталізований Життєвий Цикл Ініціалізації Payload Config**:
   - **1. Валідація вхідного конфігу**: Перевірка базової структури об'єкта, переданого в `buildConfig({ ... })`.
   - **2. Виконання плагінів (`plugins` array)**: Payload по черзі викликає функції плагінів z масиву `plugins: [...]`. Кожен плагін отримує поточний `config`, мутує або додає колекції/поля/хуки і повертає оновлений конфіг.
   - **3. Інтеграція дефолтних опцій**: Payload заповнює відсутні поля системними значеннями (мовою за замовчуванням, i18n, системними колекціями `payload-migrations` тощо).
   - **4. Санітизація**: Перевірка унікальності слайгів колекцій, нормалізація полів, валідація схем та підготовка `importMap` для React Admin UI.
   - **5. Фінальна ініціалізація**: Створення готового екземпляра Payload (підключення БД, реєстрація REST/GraphQL та запуск).

3. **Автономність та Розділення (OLMUI & Subpath Exports)**:
   - Логіка плагіна (`src/index.js`) не повинна імпортувати чи залежати від React-компонентів адмінки.
   - Компоненти UI адмінки експортуються через додаткові субшляхи (наприклад, `@nan0web/payload-self-storage/admin`).

4. **Чисті Рядкові Ідентифікатори Компонентів**:
   - Усі React-компоненти для Admin UI підключаються у конфігу Payload тільки за допомогою рядкових шляхів (`'package-name/subpath#ExportName'`).

5. **Використання Local API (`getPayload`)**:
   - Всі серверні операції та скрипти розробляються через збалансований Local API з урахуванням конфігурацій `context` та `overrideAccess`.
